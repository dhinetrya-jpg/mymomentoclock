# Payment security review

Fixed: arrival-order ambiguity, publicly constructible verified-event struct, missing durable application access queries, client-selected ownership risks, in-memory/provider retry gaps and absent service transport. Existing fake/unsigned routes remain disabled. No duplicate Node database or React-only authorization was introduced.

Controls: opaque verified evidence; raw provider verification boundary and latest snapshot; immutable server catalog; exact integer amount/currency/identity matching; composite owner/provider foreign keys; transactional locks/state/grant/audit; unique namespaces/event/payment/idempotency; terminal revocation; ownership SQL predicates; authenticated server access checks; mTLS dedicated CA+SAN plus user token re-verification; strict allowlists/bounds/timeouts and redacted errors. Database opener insists verify-full, rejects ambiguous URL overrides, pool/time limits and readiness; secret file supported. Runtime role lacks DELETE/DDL; migration owner separate. No raw signed body/card/astrology metadata. No public reconciliation/diagnostics/test adapters.

Fixtures are in _test.go and tests/payment files, not production registration. The end-to-end fixture route is created only inside httptest, not in main or Node runtime. NewService rejects nonproduction-ready test adapters in production even with approval supplied. Default Node boundary is dependency-free503. No environment variable activates a mock. Node's production code cannot load test adapter by a request or config name.

Event conflict policy is fail closed: the first durable fingerprint owns an event ID; a conflicting payload never replaces it. If invalid evidence wins that race, legitimate delivery conflicts and requires reconciliation; it does not produce unauthorized access. Authoritative revisions and value/ownership checks are mandatory before any grant. Store queue is durable independently of fulfillment transaction, so rejected/retry records remain without a partial order/grant.

Residual dependencies: real identity/session policy; selected provider/account/signing/replay/ordered-state contract; owner-approved catalog/pricing/access-expiry/partial-refund policy; production DB/TLS/roles/migrations/backups; internal CA/cert rotation and provider egress; approved event retention; provider sandbox, live infrastructure and restore drills. No production activation or real financial transaction is proven. ProductionReady assertions must be reviewed, not treated as cryptographic adapter attestation. Only reviewed application code may inject dependencies; DI is not a sandbox against malicious repository code.

Operational limits: aggregate existing public limits remain, internal listener timeouts/pool/socket/body limits are bounded. No distributed abuse-control/capacity claim or external penetration/dependency advisory audit. Audit hashes pseudonymize identifiers but do not anonymize financial records. Retention/deletion requires owner/legal policy; no destructive retention worker enabled.

Second sweep must examine legacy root/backend callbacks, Node forwarding, frontend storage/callback success, original schema tables, test-only fixture reachability, signature/seal paths, event ID/namespace handling, active/revoked/expiry joins, post-commit retries and deployment exposure. Actual sweep outcomes and any corrected defects are recorded in the final test report/handoff.
